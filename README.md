# Terraform Demo：阿里云 ECS + 本地 K3s 环境

> 这是一个**公开项目**。它演示的不只是「怎么用 Terraform」，而是**怎么把一组工程判断做成可执行、可复核的证据** ——
> Terraform 能管什么、不能管什么；边界怎么在代码里守住；环境变更怎么收敛到一条路径。
> 这里的判断都尽量落到可执行的检查或可对照的登记表上，而不是只写在文档里。

本文说明**项目背景、设计目标、关键取舍，以及如何独立复核这些结论**。
代码如何组织、命令怎么执行、实践中遇到哪些问题 —— 见 [`LOGIC.md`](LOGIC.md) 与 [`PITFALLS.md`](PITFALLS.md)。

适合三类读者：正在使用 Terraform、想弄清它能管到哪一步的人；手上已有运行中的环境、需要判断能否接管的人；
以及关心「工程判断如何被固化成可执行检查」的人。

## 1. 项目背景

这个仓库从第一天起就按「**可公开、能被陌生人独立复核**」的标准写，原因与下面三个场景有关。

### ① 公有云练习环境：可创建，也要能彻底删除

公有云部分从零创建 VPC、交换机、安全组与 ECS，全部显式声明为**按量付费、可整组删除**。

强调「可整组删除」，是因为练习的隐性成本不在费用，而在**不确定资源能否删净**：
一旦出现删不掉的资源、或删除后仍在计费的实例，后续每次实践都会因此受限。

因此云端部分的目标不是功能数量，而是**一条命令创建、一条命令删除、删除后不产生残留计费**。

### ② 已存在的环境不适合用 Terraform 接管

本地两台节点（K3s 主 / 从）是**既有环境**，其上运行 Jenkins、Harbor、GitLab 等服务。
常规做法是用 Terraform 把它们接管进 state，但本项目的一个重要结论恰恰相反：

> **在 VMware Workstation 场景下，这件事既做不到，也不应做。**

原因很具体：VMware Workstation 没有官方 provider；`null_resource` 并不持有虚机对象，
它只记录「这段脚本是否执行过」，因此无法通过 import 接管。

**于是本地部分采用另一条思路：不创建虚机，只盘点现状，并以代码声明容器之上的配置。**
默认状态下它不修改机器上的任何内容，只输出盘点结果供核对。

这条结论比代码本身更有价值 —— 它把模糊的问题变成了可判断的规则：
**一个资源能否纳入 Terraform，取决于它是否有 provider、是否支持 `read`、以及它是否只有 Terraform 一个声明式来源。**

### ③ 批量操作需要区分「可自由变更」与「默认只读」的目标

云上资源完全由本项目创建，可以自由变更；本地节点是既有环境，其上运行着其他用途的服务。
`ansible/` 这一层正是为这个差异而存在：**同一套 playbook，对云上资源完全开放，对本地节点默认不做任何修改。**

它并非「顺带加的一层自动化」，而是有意设计成「默认只读、变更需显式解锁」，
并且这一性质由静态检查保证，而不是依赖使用者的自觉。

## 2. 设计目标

### ① 让 Terraform 的能力边界可判定，而不是靠经验判断

整套结构背后的判断依据可以概括为一句话：

> **Terraform 只能管理「它能够创建」、或「有 provider 支持 `read`」、或「它是唯一声明式来源」的资源。**

由此推出的分层是：

| 层次 | 归谁管 | 原因 |
|---|---|---|
| 虚拟机本身 | VMware Workstation（手工 / vmrun） | 无 provider，无法 import |
| 操作系统配置 | 配置管理工具（Ansible） | 不是 Terraform 的强项 |
| 容器进程 | docker compose | compose 文件本身即为声明式配置，无需第二个声明源 |
| 容器之上的配置（Harbor 项目 / webhook、Jenkins 任务、GitLab 项目 / webhook） | Terraform | 走 HTTP API，与安装方式无关，适合声明式管理 |

这张表是「为什么 Harbor 无法整体接管、为什么 K8s 工作负载不进 Terraform、为什么 state 需要加锁」这一整串决定的由来。

### ② 边界写在文档里等于没写，必须可执行

「谁管什么」在文档里很容易达成一致，**难的是它在代码中不被逐渐侵蚀**。
因此九条边界每一条都配有一个纯标准库、不连机器、不装依赖的静态检查（`tools/check_boundaries.py`），
该检查自身还有 65 个用例证明「确实会触发」—— 一个永远不会报错的检查，比没有检查更糟。

同样，跨层衔接（云机器 IP 从 Terraform 传到 Ansible）不依赖约定，而是**默认为零条，每条都必须写进
[`boundaries.yml`](boundaries.yml) 供 review**；不参与运行的路径也必须登记在册，而不是靠目录名推断。

### ③ 环境变更应收敛到唯一入口

因此 `.gitlab-ci.yml` 是**环境变更的唯一入口**：`validate → plan → apply（人工放行）→ configure → verify`。
变更类动作必须由人确认放行，且 `apply` 使用的是 `plan` 阶段产出的那份计划文件 ——
否则「人工放行的那一下，批准的可能不是所看到的那份计划」。

这里存在两条**不同**的流水线，容易混淆，因此刻意分开设计：

- **环境变更**（改基础设施）：`.gitlab-ci.yml`，执行 Terraform 与 Ansible 本身。
- **应用交付**（改应用）：Harbor webhook → Jenkins，以及 GitLab push 触发构建。

两者都与 GitLab 相关，但变更对象完全不同，且**不能互相调用** —— 否则「谁对环境状态负责」将无法界定。

## 3. 关键取舍

| 取舍 | 选了 | 没选 | 理由 |
|---|---|---|---|
| 本地部分 | 盘点现状 + 声明容器之上的配置 | 用 Terraform 接管虚机 | 没有 provider，`null_resource` 也无从 import |
| 容器编排 | 由 docker compose 自行管理 | 让 Terraform 覆写 compose 文件 | compose 文件本身即为声明式配置，不引入第二个声明源（默认 `jenkins_manage_compose = false`） |
| Harbor | 只声明项目与 webhook | 接管整个容器栈 | 官方默认部署约 9 个容器，整体接管不可行；`manage_harbor` 在代码中固定为 `false` |
| K8s 工作负载 | K8s YAML / Helm / GitOps | 写进 Terraform | 基础设施节奏（集群是否存在）与应用发布节奏（何时发这版）是两件事 |
| Ansible 的位置 | 独立一层，不与 Terraform 互相调用 | 作为 Terraform 的触发器 | 否则 `apply` 返回成功、后续步骤失败时，state 仍记为成功 |
| 数据如何跨层 | CI 中通过 artifact 传递，本地手工执行时使用声明文件 | Ansible 自行调用 `terraform output` | 前者使 Ansible 侧不需要持有云凭证 —— 越界在能力层面即不可行，而非依赖约定 |
| state | 模板已备好（OSS + TableStore 锁），默认不启用 | 默认启用 | 启用前需先有 OSS 桶与 OTS 锁表，默认启用会让 `terraform init` 直接失败 |
| 本地服务器 | 默认只读，变更需显式解锁 | 与云上资源同等管理 | 本地节点为既有环境，其上运行其他用途的服务；该性质由静态检查保证 |

## 4. 如何复核这个项目

上面的结论不需要相信本文的叙述，可以自己验证：

```bash
python3 tools/check_boundaries.py             # 九条边界逐条检查，并复核 boundaries.yml 的衔接登记
python3 tools/check_boundaries.py --selftest  # 证明检查器确实会响：65 个用例，该拦的拦、该放行的放行
```

- 检查器**只用 Python 标准库**，不连云、不连机器、不装依赖，在任何机器上都能复现同一结果。
- 跨层衔接、以及「不参与运行因而也不参与检查」的路径，都登记在 [`boundaries.yml`](boundaries.yml)，可逐条对照。
- 文档分成三份，是为了让三类问题各有入口：结论与理由（本文）、实现与操作（[`LOGIC.md`](LOGIC.md)）、
  失败模式（[`PITFALLS.md`](PITFALLS.md)，49 条，含**没有验证过的部分**）。

## 5. 适用范围与限制

为避免预期错位，边界也从另一面说明：

- **不是生产模板。** 它刻意采用单模块与本地 state（提供远程后端模板但不默认启用），
  面向「单人、单机、快速创建与销毁」的场景。多人协作前必须切换远程后端。
- **不是「最佳实践合集」。** 这里的每条规则都对应一种真实的失败模式；
  没有对应失败场景的规则，本仓库不会收录。
- **不是一键部署。** 本地节点不会被创建，默认也不会被修改 —— 本项目关注的是
  「已存在的资源如何被安全地声明式管理」。
- **不假设 Docker Hub 能连通。** 国内多数区域直连 `registry-1.docker.io` 会超时，
  拉不到镜像时 playbook 会明确停在「镜像就位」这一步并给出三条路（加速器 / 离线包 / 换镜像），
  而不是让 `docker compose up -d` 用一句 `i/o timeout` 收场（见 [`PITFALLS.md`](PITFALLS.md) 第 47 条）。
- **不是验证报告。** 哪些经过真机验证、哪些只在本地运行过，在
  [`LOGIC.md` 的「验证状态」一节](LOGIC.md#验证状态) 中逐条列出，包括**未验证的部分**。

## 7. 成本与安全提示

- **云端资源按量付费，实例存在期间持续计费。** 练习结束请执行 `terraform destroy`。
  建议在独立的测试账号中操作；如账号内已有生产资源，请勿执行 `apply`。
- **本地部分默认只读**，首次 `apply` 不会修改任何内容。开启管理前，请先用盘点输出核对自己的实际配置。
- **Jenkins 容器以 `privileged: true` + root 运行并挂载 `docker.sock`，等价于宿主机 root 权限**，
  不应暴露到公网。
- 完整的成本与风险清单（含 GitLab、Harbor 与端口 8081 相关问题的说明）见
  [`LOGIC.md` 的「成本与风险提示」](LOGIC.md#成本与风险提示)。
